## 5. Фиксированная вместимость — завершена

По запросу пользователя убрать продуктовые ограничения «8 сцен», «512 KiB на файл»
и «128 кадров». Число сцен и кадров определяется размером данных и безопасной
работой устройства; внутренние защитные границы парсера остаются обязательными,
но не должны становиться прежним фиксированным лимитом интерфейса.

Уточнённая политика: один константный максимум суммарного размера живых asset
файлов библиотеки, без пользовательских настроек объёма/количества и без
динамического продуктового лимита в зависимости от состава библиотеки.
Flash остаётся 4 MB. 10% вычитаются из рассчитанного безопасного максимума
библиотеки, а не задаются как отдельное требование свободных 10% Flash.

- Рассчитать максимальную библиотеку L для худшего случая: один asset занимает
  весь L; безопасная замена требует одновременно старую библиотеку и новую
  копию размером L. Условие: 2L + S <= T, где T — ёмкость LittleFS, S — бюджет
  metadata/manifest/atomic commit с учётом числа файлов и пиков операций.
- Зафиксирована LIBRARY_MAX_BYTES = округлить_вниз(0.9 * (T-S)/2).
  Windows-модель LittleFS2.11 с большим manifest выявила metadata overhead
  порядка132 KiB. Выбран S=160 KiB: (1984-160)/2=912 KiB, минус10%=820.8 KiB;
  округление вниз до4 KiB даёт **820 KiB (839680 байт)**. Предварительный
  кандидат832 KiB заменён этим значением. Пользователь квоту не настраивает.
- Ограничить итоговую сумму живых файлов этой константой, а размер одиночного
  файла — тем же пределом. Число сцен/кадров ограничивается этим бюджетом и
  проверенными ресурсами индекса/metadata, без прежнего продуктового лимита 8.
  Каждый файл округляется вверх до4 KiB; максимум205 записей выведен из квоты.
  Не обещать буквально бесконечное число крошечных файлов: их metadata тоже
  должны укладываться в подтверждённый бюджет S.
- При upload всё равно проверять фактический free для временной записи и commit;
  при неожиданной нехватке места безопасно отказывать. Удаление остаётся
  доступным; никогда не удалять пользовательскую сцену автоматически.
- Убирать устаревшие неактивные A/B файлы только после подтверждённого durable
  manifest commit, с восстановлением после сбоя; не считать их живым контентом
  и не обещать место, пока оно фактически не освобождено. Проверить orphan cleanup.

Расширить manifest/ID, capabilities, перечисление сцен, плейлист, GUI, RAM cache,
CLI и архивы согласованно. Для больших списков/индексов использовать ограниченные
порции и потоковое чтение вместо массивов на все кадры или full-screen framebuffer.
Desktop ограничивает RAM при декодировании preview, сохраняя быстрый выбор сцен
без повторных USB чтений. Старые assets, сцены и команды должны оставаться читаемыми;
добавления API объявлять через capabilities. До реализации проверить ограничения
пакетов protocol v1, размера manifest и времени CRC/загрузки.

Показывать в GUI заполненность библиотеки относительно фиксированного максимума;
прогноз upload/замены/удаления считать по реальным файлам. При нехватке
места объяснять причину до записи. Проверить near-full upload/edit/delete,
прерывание и потерю питания на commit/cleanup, сохранность всех старых сцен,
LCD и hardware RESET. Не переходить на Flash 8 MB.

Firmware1.7/bit6, команды22–28, GUI/CLI/архивы реализованы. На плате прошли
17 сцен при полной квоте, безопасная замена, 12-сценный плейлист, 1000 кадров,
invalid/interrupted upload и программный RESET. Существующие assets сохранены;
ID2 и8 удалены только по явному согласию пользователя после полного backup.
После паузы пользователь самостоятельно очистил библиотеку. На пустой плате
дополнительно проверены 205 реальных сцен с 48-byte escaped titles, полная квота,
замена, порядок и плейлист из205 записей, RESET и побайтовое чтение всех205 assets.
Файл770684 байта (7 полноэкранных кадров) загружен и безопасно заменён.
Нагрузка выявила watchdog при boot cleanup: добавлены уступки CPU в длинных циклах
и пропуск полной проверки assets, когда удалять нечего; watchdog не отключён.
После исправления USB готов через1.3 секунды, повторный RESET без reset loop.
Все205 нагрузочных сцен удалены по отдельному явному разрешению пользователя;

## 6. Сжатие анимаций и изменённые области — реализована, аппаратная проверка

Firmware1.8/bit7 и encoding1 внутри animation asset v1 реализованы. Автоматически
выбираются raw/RLE полного кадра либо прямоугольника изменений; ключевой кадр
минимум раз в32 кадра, декодирование через прежний5120-byte DMA strip. Прежние
static и raw animations сохранены. GIF-окно считает фактический оптимизированный
файл в фоне, показывает экономию и проверяет библиотеку/безопасную запись.
На плате прошли70 кадров128×128 (27428 Б) и40 кадров320×172 (17752 Б), exact
readback, повреждённые записи, прерванная замена/программный RESET, raw fallback
и измерение времени/RAM. Ожидается подтверждение пользователем LCD/hardware RESET.
Дополнительно проверены581 полноэкранный кадр на границе32 MP preview: файл18632 Б,
ACK4.906 s, RESET/readback. Ускорена CRC-проверка длинных RLE runs без их распаковки;
все проверки сохранены. 121 desktop +9 tools tests прошли. Общий RAM бюджет
распакованных preview32 MP не затрагивает verified asset cache и не вызывает USB reads.
См. [формат и измерения](animation_compression.md).

После безопасного расширения вместимости сравнить на реальных GIF два алгоритма:
RLE для RGB565 и delta frames с прямоугольниками изменённых областей. Рассмотреть
их сочетание; сохранять raw кадр, когда сжатие увеличивает размер. GIF остаётся
входным форматом desktop; декодирование GIF на ESP32 не требуется.

Desktop корректно композитит transparency/disposal, затем кодирует точные
выходные RGB565 пиксели. Использовать независимые ключевые кадры и ограниченные
цепочки delta, чтобы restart/loop/восстановление не требовали бесконечного replay.
Firmware декодирует полосами в ограниченную RAM, без full-screen framebuffer;
добавить проверки размеров, границ прямоугольников, длины распаковки и CRC.
Сохранить static v1 и текущие raw animations; новый encoding объявлять capability,
не менять смысл существующих файлов. Формат расширения документировать до записи.

Сравнить размер, FPS, время USB upload, CPU/RAM и восстановление после RESET на
GIF с малым движущимся объектом, полной сменой кадра, шумом и прозрачностью.
Preview должен декодировать точные отправляемые данные. Показать пользователю
итоговый размер/длительность и ограничения, не обещать фиксированный коэффициент
сжатия или неограниченную длительность. Применять резерв места из фазы 5.

## 7. Понятные уведомления и технические подробности — реализована, проверка desktop

Добавлены shared Problem reports, окно с простым объяснением/следующим действием,
«? Подробнее», копирование, очередь непрочитанных ошибок, dedup подключения и
отключаемый звук. Worker exceptions, local validation, startup и preferences
подключены; unknown commit и post-commit preview failure различаются. Firmware
не менялась. См. [поведение и диагностику](notifications.md).
138 desktop +9 tools tests и19 packaged smoke checks прошли. Новая portable
собрана отдельно в `.pio/notifications-dist`, пока прежняя `.exe` открыта;
осталось закрыть прежний экземпляр, заменить обычную сборку и подтвердить UI.

Требование пользователя: приложением пользуется человек без технических знаний;
ему нужно явно понять проблему и следующее действие, а разработчику получить
точные диагностические сведения. Применить единый механизм ко всем операциям:
подключение, подготовка/редактирование, upload, удаление, библиотека, плейлист,
storage, восстановление и запуск приложения. Не оставлять ошибки только в логах
или незаметной строке статуса.

- Блокирующая ошибка открывает диалог поверх окна приложения: короткий русский
  заголовок, понятная причина без traceback/кодовых названий, состояние операции
  и конкретное действие («Подключить заколку», «Выбрать другой файл», «Закрыть»).
  Не обещать сохранность/успех без проверки; при обрыве commit явно сообщать,
  что результат ещё не подтверждён, и предложить проверку после подключения.
- Возле каждой ошибки — заметная дружелюбная кнопка «? Подробнее».
  Она раскрывает техническую панель: код ошибки, операция/этап, ожидаемое и
  фактическое состояние, ACK/NACK/timeout, версии приложения/firmware/protocol,
  известные параметры устройства, размеры/CRC/свободное место по ситуации,
  причина исключения и релевантный traceback. Отмечать неизвестные сведения,
  не подменять их догадками. Добавить «Скопировать отчёт» для отправки разработчику.
- Не включать в копируемый отчёт изображения, их содержимое, секреты или лишние
  персональные пути; идентификаторы устройства/имена файлов включать только
  необходимые для диагностики, с явным отображением перед копированием.
- Обычные успехи/предупреждения тоже видимы: понятное уведомление у операции,
  результат и следующий шаг. Диалоги нужны для ошибок, блокирующих работу,
  важных предупреждений и подтверждений разрушительных действий; прогресс и
  каждый успешный шаг не должны создавать поток модальных окон.
- Для недоступного действия объяснять причину рядом с кнопкой; при попытке
  выполнить действие показывать понятное сообщение, а не молча игнорировать.
  Ошибки не исчезают до прочтения; фокус клавиатуры и DPI должны работать.
- Необязательный короткий звук ошибки с настройкой отключения. Визуальное
  уведомление обязательно независимо от звука. Повторные polling/reconnect
  ошибки объединять, не создавать бесконечные диалоги и звуковые сигналы.
- Обрабатывать ошибки worker threads и необработанные исключения через тот же
  механизм с записью в user-data log. Не блокировать serial/image workers
  ожиданием UI. Не повторять interrupted upload автоматически.

Проверить mock-сценарии: нет платы, занятый порт, disconnect в upload/read,
нехватка места, повреждённый/неподдерживаемый файл, stale scene, NACK, ошибка
библиотеки/диска. В каждом случае пользователь видит понятный следующий шаг,
а скопированный отчёт позволяет точно определить причину. Проверить реальные
disconnect/reconnect и видимость диалогов в portable .exe.
Базовые уведомления для новых ограничений фазы 5 внедрять вместе с ними;
эта фаза унифицирует сообщения всего приложения.

## 8. Качество статичных изображений и живой preview — завершена

Реализация и локальный формат проектов описаны в `docs/image_quality.md`.
Desktop автоматически проверяет качество, exact RGB565 preview, сохранение
исходника/параметров и совместимость GIF/pixel-art; пользователь подтвердил LCD
и проекты, исправленные кнопки резкости и новую раскладку интерфейса.

Пользователь согласовал улучшение уменьшения изображений: Lanczos для фото/рисунков,
настраиваемая умеренная резкость после resize, необязательный dithering при
квантизации RGB565. Реализованный pixel_art использует NEAREST без фильтров;
обычный режим по умолчанию — Lanczos, прежний Bicubic доступен отдельно.
Это обработка статичных изображений, не изменение GIF pipeline.

Настройки алгоритмов/фильтров расположить рядом с видимым preview: любое изменение
сразу обновляет точный декодированный выходной RGB565 в отдельном worker,
с debounce/cancellation устаревших результатов без зависания UI. Дать сравнение
до/после, увеличение для оценки пикселей, reset обработки; при drag сохранять
непрерывное отображение. Сначала resize, затем резкость, затем RGB565/dithering;
фон/прозрачность и crop должны обрабатываться предсказуемо.

Preview показывает результат на 320×172, а не обещает восстановить детали,
которых нет в уменьшенном изображении. Сохранить понятные FIT/FILL/crop/позицию.
Новый формат файла ради фильтров не вводить: выход — существующий static asset v1.
Сохранять локальный исходник и параметры обработки для повторного редактирования;
старый RGB565 без исходника остаётся редактируемым, но исходные детали не восстановить.
Проверить фото, мелкие линии/текст, градиенты, прозрачность и pixel art;
сравнить preview/LCD и отсутствие зависаний при крупных допустимых исходниках.

шрифт, размер, цвет, выравнивание, перенос, положение drag/числами, при необходимости
обводка/фон для читаемости. Поддержать несколько редактируемых слоёв, порядок,
удаление и undo/redo; preview отображает итоговые пиксели экрана.
Шрифты растеризуются на desktop; не вводить TTF/OTF renderer в firmware.

Статичный текст запекается в обычный static asset v1. Локальный проект сохраняет
текст/слои/исходник, а не только flattened RGB565; после чтения старого asset с платы
не обещать распознавание текста или восстановление слоёв.

Для движения текста слева направо и справа налево добавить скорость, направление,
паузы/цикл и живой preview. Воспроизведение должно работать без desktop и после
RESET. Сначала оценить генерацию кадров в совместимый animation encoding после
фазы 6: статичный фон и изменённые области текста, с расчётом размера/FPS.
Если это не обеспечивает достаточную длительность/плавность, отдельно описать
capability-расширение для bitmap-полосы текста и bounded strip rendering.
Не заявлять бесконечный scroll на конечном наборе кадров без проверки шва цикла.
Сохранить compatibility, безопасный upload и ограничения памяти фазы 5.

## 10. Рисование пикселями

Добавить отдельный режим создания рисунка на холсте логического LCD 320×172:
кисть/карандаш с размером и цветом, ластик (прозрачность слоя либо заданный фон),
палитра/пипетка, заливка, очистка с подтверждением, undo/redo. Zoom и панорамирование,
опциональная сетка и точное соответствие курсора пикселям при Windows DPI.
Видимый рядом preview реального размера обновляется во время рисования.

Разрешить рисование отдельным слоем поверх изображения и текста, без изменения
исходника. Хранить редактируемый проект локально; экспорт/загрузка результата
на заколку — обычный static RGB565 asset v1 через existing A/B commit.
Новая сцена не перезаписывает старую без подтверждения, сохранение на плату
показывает ACK/проверку регистрации и фактическую память. Проверить повторное
открытие проекта, offline работу, preview/LCD и сохранность рисунка после RESET.

## 11. Автономность и управление

Изучить реальную схему кнопок/питания, затем управление сценами, яркость, аккумулятор
и сон. Измерить время работы/нагрев и проверить LittleFS при потере питания.
Wi-Fi/Bluetooth/Flash 8 MB не входят автоматически ни в одну фазу.

## 12. Публичное распространение

Версии/история изменений, иконка/сведения о приложении, диагностика и проверки
на чистых Windows 10/11. Installer/цифровая подпись — при необходимости;
portable ZIP сохраняется. Можно вести параллельно после выбора состава первого релиза.
