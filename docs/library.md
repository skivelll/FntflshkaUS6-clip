# Локальная библиотека и резервные копии

Firmware1.7: актуальные лимиты, pagination, quota и cleanup описаны в
[library_capacity.md](library_capacity.md). Ограничения восьми сцен/512 KiB
в описаниях предыдущих версий ниже относятся к legacy firmware.

Окно «Библиотека…» доступно из основной панели. Для просмотра локальных коллекций
USB не нужен. Firmware 1.2, USB protocol v1, asset v1 и Flash layout не меняются.

## Обычный workflow

1. Подключи плату и дождись начальной загрузки assets в RAM.
2. Открой библиотеку, задай название, нажми «Сохранить все сцены с платы» или
   «Сохранить одну сцену…» и выбери ID. Экспорт использует проверенный RAM-кэш,
   без повторного READ_SCENE; snapshot и checksum сверяются перед экспортом.
3. Коллекция появится слева. Выбери сцену в её списке: preview отображает точный
   RGB565, центрированный на экране сохранённого размера.
4. «Экспорт коллекции…» сохраняет переносимый `.fclip` в выбранное место.
   «Импорт архива…» проверяет файл и создаёт отдельную локальную копию.
   Повреждённые файлы отклоняются до любых USB-записей.
5. Для восстановления выбери коллекцию и нажми «Восстановить на заколку…».

Библиотека — каталог `library` рядом с `logs/settings.ini` в user-data directory.
Кнопка «Папка библиотеки» открывает его. Реальный режим, demo и smoke используют
свои каталоги. Архивы создаются только по явному экспорту/импорту либо перед
подтверждённым восстановлением. Автоматический scene cache по-прежнему живёт
только в RAM; USB trust не сохраняется на диск.

Исходные PNG/прозрачность/параметры редактирования не входят в резервную копию
уже залитой сцены: на плате есть лишь готовый RGB565. Локальные проекты с исходниками
могут быть отдельной следующей задачей. Копия содержит финальные assets, названия,
относительный порядок и активный ID.

## План восстановления

Для каждой сцены выбери:

- «Добавить в свободное место» (по умолчанию). Если исходный ID свободен,
  он сохраняется; иначе выбирается свободный ID 1–8.
- «Заменить ID N» — явная замена конкретной сцены, со сверкой старого checksum.
- «Пропустить» — эта сцена не записывается.

Кнопка сопоставления по ID явно назначает замену совпадающих ID и оставляет
остальные как добавление. Дубли целевых ID, нехватка мест, неподходящие размеры
и нехватка памяти блокируют подтверждение. Ни одна сцена вне плана не удаляется.
Неназначенные существующие сцены сохраняются; их относительный порядок остаётся.
При включённом применении metadata восстановленные сцены размещаются после них
в порядке коллекции, названия берутся из архива. Без этого флага replacement
сохраняет прежнее название/порядок через существующий A/B commit.

План показывает ID добавления/замены, будущий порядок и ACTIVE. Применение имён/
порядка доступно по capability firmware 1.2. Сохранённый активный ID переводится
в назначенный ID. Если он пропущен или в архиве нет активной сцены, сохраняется
прежний активный ID; если его нет, активируется последняя добавленная сцена.
API v1 не умеет отдельно выбрать встроенное demo без удаления активной сцены;
восстановление архива с `active_id=null` не обещает такой переключатель.

Оценка места консервативна: сумма длин assets + 4096 bytes на каждый файл +
8192 bytes общего запаса. Это оценка, не гарантия блоковой аллокации LittleFS.
Старые A/B slots не вычитаются заранее. Каждый upload отдельно проверяет реальный
free и требования firmware. Точное свободное место обновляется после ACK.

До первой записи сохраняется `before-restore-*.fclip` с прежним содержимым платы.
Если эту копию нельзя записать или кэш неполон, восстановление не начинается.
Полная копия требует возможности чтения assets (обычно firmware 1.1+) и готового
кэша. На пустой плате предварительная копия не нужна.

## Обрыв и отмена

Восстановление набора не является одной атомарной транзакцией. Каждый asset
использует существующий безопасный A/B upload; имя меняется отдельным atomic
manifest commit, итоговый порядок и ACTIVE — после файлов.

«Остановить восстановление» выставляет cancellation flag. При обрыве/остановке
уже завершённые файлы остаются, текущая незавершённая сцена защищена A/B commit,
но потерянный ACK не позволяет обещать, что commit не состоялся. Приложение
показывает ID файлов с ACK и последнюю операцию, не повторяет upload автоматически.
После подключения проверь список, имена, порядок и ACTIVE; при необходимости
создай новый план или используй предварительную копию.

После прерванного upload firmware может требовать аппаратного RESET/USB reconnect
для очистки временного upload state. Программное открытие COM не гарантирует это.
Никакого erase/форматирования или удаления лишних сцен для восстановления нет.

## Desktop archive v1

`.fclip` — ZIP-контейнер, отдельный от firmware asset/protocol format.

```text
collection.json
assets/0001.bin
assets/0002.bin
...
```

JSON содержит `format="fntflshka-us6-clip-collection"`, `version=1`, `title`,
`created_utc`, `display=[width,height]`, `active_id` (ID или null), `scenes`.
Запись scene: `id`, последовательный `order` 0…N−1, `title`, строгий `asset` path,
`sha256` всего asset. Asset v1 внутри не перекодируется и не изменяется.

Проверяются: не более205 уникальных ID1–65535, UTF-8 title до48 bytes, размеры/CRC
asset/header, SHA256, наличие ACTIVE, версия/порядок/состав архива. Лимиты:
5 MiB входного ZIP, 64 KiB JSON, 820 KiB на asset, максимум206 entries;
суммарно не более4 MiB распакованных assets. Это offline guard; квота устройства
820 KiB проверяется отдельно при восстановлении. Legacy collections читаются.
Firmware1.6 поддерживает animation type2 внутри прежнего контейнера version1;
preview анимаций готовится в library worker и проигрывается offline из RAM.
Не принимаются лишние/повторные entries, symlinks, шифрование, посторонние пути,
неизвестная версия и JSON duplicate keys. ZIP не извлекается на filesystem.
SHA256/CRC служат контролем целостности, не цифровой подписью.

Локальная запись атомарна: временный файл в том же каталоге, flush/fsync,
`os.replace`. Ошибка не оставляет обрезанную предыдущую резервную копию.
Нет новых runtime dependencies. Архивы/отчёты/пользовательские данные не входят в Git.

## Проверка

Автотесты покрывают archive roundtrip, Unicode, CRC/SHA/path/duplicate/symlink/size
rejection, atomic save failure, offline GUI, полный/одиночный экспорт без asset reads,
планы конфликтов/места/размеров/identity, порядок ID, mandatory backup, частичный
обрыв и cancellation без retry. Serial operations остаются в device worker;
ZIP/file IO и подготовка offline previews — в отдельном library worker.

Проверено 2026-10-15 на Windows 11 / Python 3.12.10:

- 79 desktop tests + 8 tools tests: PASS; `pip check`, `compileall`,
  `git diff --check`: PASS. Runtime dependencies не обновлялись.
- Переносимая Windows-сборка: ZIP 52,932,256 bytes; exe SHA256
  `e61524c99cb980f82961b3d91dc8e5c468df7562d9693d7d058fafdde8910544`.
- Распакованный ZIP с Unicode-путём/cwd вне repo/без Python в PATH:
  13 native GUI smoke checks PASS за 3.781 s, 114 event-loop ticks, 0 asset reads
  в mock. Включены экспорт/import/offline preview/restore с предварительной копией.
  Screenshot библиотеки проверен.
- Реальная плата: только чтение экспортировало семь текущих сцен в полную
  коллекцию и ACTIVE ID 1 в одиночную коллекцию. Asset reads — 7 (по одному на
  сцену), оба архива перечитаны и побайтово сверены; snapshot до/после совпал.
  COM3, firmware 1.2, порядок `2,1,3,4,5,6,7`, LittleFS total/free
  `2031616/1024000`, время 47.109 s. Коллекции сохранены в user-data library.
- Пользователь подтвердил восстановление одиночной коллекции в свободный ID 8:
  картинка на LCD совпала с preview. После отключения USB коллекции и их preview
  остались доступны; USB подключён обратно. Физическая проверка завершена.

Редактор предыдущей фазы закоммичен локально как `2eb0e15`, без push.
Firmware не менялась/не прошивалась. C host tests не выполнялись: native C11
compiler отсутствует; эта фаза изменяет только desktop/Python.
