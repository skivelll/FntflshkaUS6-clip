# Фаза 4: анимации — замеры и предложение

Исторический этап замеров firmware1.5 и согласования. Пользователь утвердил оба
профиля: компактный и полный экран. Codec/GIF GUI/playback реализованы в1.6,
оба профиля и сохранение после аппаратного RESET подтверждены пользователем.
Актуальная спецификация и лимиты —
[animation_format.md](animation_format.md); текст предложения ниже сохраняет контекст выбора.

## Реальные измерения 2026-10-15

Waveshare ESP32-C6-LCD-1.47, ESP-IDF 5.5.3, espressif32@6.13.0, Windows native.
Результаты и SHA256 firmware: [animation_benchmarks.json](animation_benchmarks.json).

| Кадр | RGB565 байт | LittleFS чтение | Чтение + вывод кадра | Измеренный потолок FPS | Upload до → после RX draining |
| --- | ---: | ---: | ---: | ---: | ---: |
| 96×96 | 18432 | 4,1 мс | 120,1 мс | 8,3 | 7,94 → 2,21 с |
| 128×128 | 32768 | 7,6 мс | 160,7 мс | 6,2 | 13,14 → 2,99 с |
| 320×172 | 110080 | 28,1 мс | 219,2 мс | 4,6 | 41,24 → 6,34 с |

Это три повтора **одного статичного кадра** через существующий renderer без
очистки экрана между кадрами; это ещё не готовая анимация/замер визуальной плавности.
Потолок FPS не включает будущие frame metadata, CRC и работу main loop между
кадрами. Не обещать 30/60 FPS. LittleFS чтение отдельно измерено пятью повторами.

Heap free 419848 байт; largest block 401408; наблюдавшийся minimum после
профилирования 409488. Это runtime показатели ESP-IDF heap, не обещание
возможности выделить framebuffer и не изменение board RAM/Flash конфигурации.
Постоянный LCD DMA buffer — 5120 байт; scratch диагностического чтения также
5120 байт, временно выделяется и освобождается. Full-screen framebuffer отсутствует.

USB PING около 20 мс, READ_SCENE около 16–17 KB/s. Старый upload упирался в
64 RX байта за tick 20 мс. Вычитывание доступных данных с лимитом 1024 байта
за tick ускорило upload полного asset в 6,5 раза без изменения framing/CRC/ACK.
Лимит не позволяет непрерывному входному потоку бесконечно задерживать main loop.

Измерения использовали только собственный временный ID8; после них он удалён.
Все семь пользовательских assets побайтово сверены с новым preflight .fclip,
названия/порядок сохранены. Плейлист возвращён: 1/5/7/6, 6 секунд, переход сверху
вниз, включён. LittleFS total/free снова 2031616/462848. Phase 4 ещё не завершена.

## Рекомендуемый первый объём

- GIF как входной формат desktop, преобразование всех кадров в RGB565 на ПК.
  ESP32 не декодирует GIF. Учитывать transparency, disposal и длительности.
- Компактные кадры до 128×128: до примерно 6 FPS для 96×96 (минимум 170 мс),
  до 4 FPS для больших кадров (минимум 250 мс). Длительности сохраняются после
  согласованного resampling; показывать пользователю фактическую длительность.
- Зацикленное воспроизведение на плате без приложения. Общие размер и положение
  для всех кадров; фон и точный outgoing RGB565 должны совпадать с preview.
- Максимум файла 512 KiB, максимум 128 кадров, минимум два. Реальное число
  ограничено также размером: 96×96 — до 28 кадров, 128×128 — до 15. При текущем
  свободном месте и reserve 8192 байта получится примерно 24 и 13 соответственно;
  окончательный fit проверять перед BEGIN с текущим free, без вычитания старого A/B.
- Автоматически не обрезать длинный GIF и не перезаписывать сцены: показать
  длительность/число кадров/байты и дать пользователю сократить диапазон или размер.
- Без RLE, delta, palette codecs, звука, видео и framebuffer в первом этапе.

Альтернатива для согласования: также разрешить кадры до 320×172 с лимитом
около 3 FPS и проверкой прототипа на LCD. При raw RGB565 в 512 KiB помещаются
только четыре полноэкранных кадра; более длинная анимация потребует отдельного
решения о компрессии/формате. Ни RAM запас, ни физические 8 MB Flash не отменяют
текущие ограничения renderer и partition layout.

## Предложение расширения asset v1 (не реализовано)

Сохранить 24-байтный `HCAS` header, version=1, RGB565=1, reserved=0. Static type=1
и его размер/CRC остаются побайтово прежними. Optional animation type=2 объявляется
новым capability bit 5; отправлять его только на firmware с этим флагом.
Header width/height — размер одного нормализованного кадра; payload size и CRC
относятся ко всему animation payload.

Предлагаемый payload, little-endian:

| Поле | Байты | Смысл |
| --- | ---: | --- |
| frame_count | 2 | 2–128 |
| loop_mode | 1 | 0 = бесконечный цикл |
| reserved | 1 | 0 |
| origin_x / origin_y | 2+2 | signed положение общей области на LCD |
| frame_bytes | 4 | width × height × 2 |
| reserved | 4 | 0 |
| frame table | count × 12 | offset u32, duration_ms u32, frame CRC32 u32 |
| frame pixels | count × frame_bytes | RGB565, полные независимые кадры |

Offsets считаются от начала payload; строго последовательны после таблицы,
без holes/overlaps/trailing data. Проверять длины с overflow-safe арифметикой,
диапазоны положения/времени, все reserved и CRC каждого кадра до commit.
Положение ограничить так, чтобы хотя бы часть кадра пересекала LCD; clip не должен
выводить чтение файла/запись DMA за границы. Header CRC и payload CRC прежние.

Новые hosts должны знать фактическую длину animation asset: предлагается optional
GET_ASSET_INFO (20, ID+expected CRC) до READ_SCENE. Формат существующих frames и
запросов READ_SCENE не менять; расширить безопасное чтение на реальную длину файла
только после проверки type/manifest. Static path остаётся прежним.

Manifest v1 получает type=2 и checksum всего payload, A/B commit прежний. Старые
статичные assets и все команды остаются рабочими. Старые GUI, которые принимают
только type=1, не обязаны показывать смешанный список с animation: для анимаций
нужна новая desktop версия. Не выдавать animation за static и не разрешать
неподдерживаемому host незаметно заменять animation ID статичным upload.

## Последующая реализация после согласования

1. Общий codec, GIF normalizer и malicious/truncated/index/CRC tests. Ограничить
   input bytes, canvas, frame count и суммарную работу decoder до обработки.
2. Firmware validation/playback с одним file handle, bounded frame index и
   существующим DMA strip. Main loop/USB обслуживать между кадрами, без Flash
   записей по таймеру. При ошибке безопасный fallback.
3. GUI импорт, настройки размера/положения/диапазона, точный анимированный preview
   в RAM. Вся подготовка в image worker; QTimer preview не читает USB.
4. Safe upload/replacement, LIST_SCENES, READ_SCENE/cache, library export/import/
   restore. Существующие .fclip со статичными assets остаются читаемыми. Увеличить
   bounded archive limits только под согласованный размер, сохранить strict ZIP.
5. Сочетание с плейлистом: dwell сцены независим от внутренних frame durations;
   ручной показ/upload/delete прекращает текущий playback. RESET начинает с
   первого кадра/первой валидной сцены. Удаление не оставляет открытого dangling file.
6. Native tests, frozen mock smoke, реальный GIF upload, LCD и аппаратный RESET.

## Диагностика firmware 1.5

`python tools/benchmark_animation.py --report .pio/benchmark.json`; optional
`--port PORT` всё равно требует HELLO identity. Команда не меняет контент или
настройки; обновляет на LCD текущую сцену и отодвигает tick плейлиста на время
замера. Нужен зарегистрированный валидный ACTIVE, свободный COM-порт и capability
bit 4. Это инструмент планирования, не импорт/проигрыватель анимаций.

89 desktop + 9 tools tests прошли. Один повтор desktop suite под нагрузкой дал
timing failure в существующем live drag тесте; повторный полный suite прошёл без
изменения GUI/ослабления теста. C host tests требуют отсутствующий native GCC/Clang.
